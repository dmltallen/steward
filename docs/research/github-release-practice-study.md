# Steward on GitHub: how mature open-source desktop products run releases

Study for the Steward release-on-GitHub decision. Researched and written 2026-11-19. Every claim carries a source in the Sources section; each source is a page read directly during this study (GitHub API output for release and workflow data, web_extract for documentation pages). Anything that could not be verified from a primary source is marked NOT VERIFIED rather than guessed.

Scope: how consumer-facing open-source desktop products actually attach and build releases, update themselves, prepare a public repo, reach winget and Homebrew, and what their release-process failures teach. Reference products examined in depth: Ollama, Jan, AnythingLLM, open-webui, plus the Tauri updater ecosystem that Jan and Steward's own design sit on.

---

## 1. Release asset practice: what real apps actually attach

I read the live GitHub releases API for each product and recorded the exact asset names and sizes, not assumptions.

### Ollama v0.40.16 (published 2026-11-09)

Assets on the release (from the GitHub releases API, 2026-11-19):

- `install.sh` and `install.ps1` (install scripts, 15.9 KB and 22.6 KB)[14]
- `sha256sum.txt` (1.4 KB, generated by the release workflow)
- macOS: `ollama-darwin.tgz`, `Ollama-darwin.zip`, `Ollama.dmg`
- Linux: `ollama-linux-amd64.tar.zst`, `ollama-linux-arm64.tar.zst`, plus variant suffixes `-mlx`, `-rocm` (amd64) and `-jetpack5`/`-jetpack6` (arm64)
- Windows: `ollama-windows-amd64.zip`, `ollama-windows-arm64.zip`, `ollama-windows-amd64-mlx.zip`, `ollama-windows-amd64-rocm.zip`, `OllamaSetup.exe` (1.8 GB)

Observed naming pattern: `ollama-<os>-<arch>[-<variant>].<archive>` for platform bundles, capitalized `Ollama.<ext>` for the clickable installers (`.dmg`, `OllamaSetup.exe`), one `sha256sum.txt` covering every payload, and shell/PowerShell install scripts committed to the repo and copied into the release by the workflow.[1][2]

### Jan v0.8.8 (published 2026-10-28)

Assets (releases API, 2026-11-19):

- `Jan_0.8.8_amd64.AppImage`, `Jan_0.8.8_amd64.deb`, `Jan_0.8.8_x64-setup.exe`, `Jan_0.8.8_arm64-setup.exe`, `Jan_0.8.8_universal.dmg`, `Jan.app.tar.gz`, `jan-mac-universal-0.8.8.zip`
- `latest.json` (the Tauri update manifest, 2.8 KB)
- dependency/source tarballs: `jan-cargo-vendor-v0.8.8.tar.gz`, `jan-yarn-cache-v0.8.8.tar.gz`, `jan-dependency-tarballs-v0.8.8.sha256` (published so builds reproduce without hitting network; a separate practice from end-user artifacts)

Observed pattern: `Jan_<version>_<arch>.<ext>` for installers (note `_x64-` / `_arm64-` for Windows), `Jan_<version>_amd64` for Linux packages, `universal.dmg` and `Jan.app.tar.gz` for macOS updater payloads, plus the signed `latest.json`. Jan does NOT publish standalone `.sig` files on the release (a HEAD request to the expected `.AppImage.sig` returned 404); the signatures live only inside `latest.json`.[3][8]

### AnythingLLM v1.20.0 (published 2026-11-17)

Assets (releases API, 2026-11-19):

- `AnythingLLMDesktop.exe`, `AnythingLLMDesktop-Arm64.exe` (Windows x64 and Arm64)
- `AnythingLLMDesktop.dmg`, `AnythingLLMDesktop-Silicon.dmg` (Intel and Apple Silicon)
- `AnythingLLMDesktop.AppImage`, `AnythingLLMDesktop-Arm64.AppImage` (Linux x64 and Arm64)
- `.AppImage.sha256` checksums for the two AppImages
- `installer.sh`, `version.txt`

Observed pattern: `AnythingLLMDesktop[-<arch>].<ext>` where the arch suffix (`-Arm64`, `-Silicon`) is only used where it differs from x64/Intel, per-file `.sha256` files (AppImages only), a text `version.txt` used for update checks, and a generic `installer.sh`.[4]

### open-webui (checked v0.13.4, published 2026-11-17)

The open-webui repo releases carry zero asset attachments (assets=0 across recent tags); the project distributes through pip/PyPI and Docker instead of GitHub release binaries.[41]

### What this means (observed, not assumed)

- Every real desktop app in this set publishes one installer or bundle per (OS, arch) as GitHub release assets, named with a consistent `<app>_<version>_<arch>` or `<app>-<os>-<arch>` scheme.
- Checksums: Ollama ships one generated `sha256sum.txt`; AnythingLLM ships per-file `.sha256`; Jan ships checksums only for its build-dependency tarballs, not the installers (the installers carry the Ed25519 signature inside `latest.json` instead).[1][4][3]
- Update manifests (`latest.json`, `version.txt`) are published as release assets on the same page.
- None of these ship GPG-signed binaries or detached PGP signatures; integrity is handled via checksum files plus (for Jan) the Tauri Ed25519 manifest, and for Ollama's installer the platform code-signing signature itself.

## 2. How per-platform builds are automated

### Ollama: trigger, matrix, runners, signing

Workflow file: `.github/workflows/release.yaml` in ollama/ollama (read in full, 894 lines).[2]

- Trigger: `on: push: tags: ['v*']`.[2]
- Every build job sets `environment: release`; that is a GitHub Environments guard in front of the signing secrets, so production signing only runs against that environment.[2]
- Runners actually used (`runs-on` labels read from the file): `ubuntu-latest` (setup and final assembly), `macos-26-xlarge` (darwin build), `windows` and `windows-<arch>` matrix entries, `linux` and `linux-arm64` (matrix). These are GitHub-hosted labels, so each platform builds natively on its own OS runner; there is no cross-compile stage for the app bundle, though the llama.cpp payloads are cross-built inside containers pushed to a registry and vendored in.[2]
- macOS signing/notarization: Apple identity secrets (`APPLE_IDENTITY`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`, `MACOS_SIGNING_KEY`, `MACOS_SIGNING_KEY_PASSWORD`) injected from the `release` environment; the workflow imports a `.p12` from a base64 secret into a throwaway keychain and calls the project's `build_darwin.sh` which codesigns and notarizes.[2]
- Windows signing: Ollama signs `OllamaSetup.exe` and the EXEs using Azure Key Vault-backed Authenticode through Google's KMS CNG plugin: the job authenticates with `google-github-actions/auth` (`project_id: ollama`, `GOOGLE_SIGNING_CREDENTIALS` secret), installs `kmscng` from the `GoogleCloudPlatform/kms-integrations` release, and signals `KEY_CONTAINER` pointing at the vault-held key; the signing command runs in `build_windows.ps1 sign`.[2]
- Final assembly job (ubuntu-latest): downloads all `bundles-*` artifacts, copies `install.sh` in, verifies a required-artifact list (fails if e.g. `OllamaSetup.exe`, `ollama-windows-amd64.zip` are missing), generates `sha256sum.txt` from every file, then creates the release as a draft prerelease with `gh release create` and uploads payloads in parallel with a retry helper, uploading `sha256sum.txt` last with `--clobber` so the checksum reflects all payloads.[2]

### Jan: reusable workflow templates, trigger, runners, signing

Workflow files: `.github/workflows/jan-tauri-build.yaml` plus reusable `template-tauri-build-{macos,windows-x64,windows-arm64,linux-x64}.yml` and `template-get-update-version.yml` in janhq/jan (read in full).[5][6][7]

- Trigger: `push: tags: ['v[0-9]+.[0-9]+.[0-9]+']`, with a concurrency group on the tag.[5]
- A `create-draft-release` job opens a draft release via `softprops/action-gh-release`; platform builds run as reusable workflows (`uses: ./.github/workflows/template-...yml`) with `secrets: inherit` and pass the tag, channel (`stable`), derived version, and `upload_url` as inputs.[5]
- Runners: the templates take a `runner` input; defaults observed in the files are `windows-2025` (x64 template), `macos-latest` (macOS template), `ubuntu-22.04` (Linux x64 template). All native, all GitHub-hosted.[6][7][40]
- macOS: imports codesign certs from base64 secrets (`CODE_SIGN_P12_BASE64`, `CODE_SIGN_P12_PASSWORD`) and notarizes with App Store Connect API creds (`NOTARY_ISSUER`, `NOTARY_KEY_ID`, `NOTARIZE_P8_BASE64`); after the build it runs `codesign --verify --deep --strict` on the bundle and checks both the `.app` and `.dmg` for a stapled notarization ticket, explicitly added so an unsigned nested binary cannot slip through Gatekeeper.[6]
- Windows: injects a signing command into the Tauri config (`jq '.bundle.windows.signCommand = "powershell ... sign.ps1 %1"'`) and signs against Azure Key Vault secrets (`AZURE_KEY_VAULT_URI`, `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_CERT_NAME`); Azure holds the cert, so no private key touches the runner.[7]
- The release manifest `latest.json` is built in a final `sync-temp-to-latest` job by jq-merging the per-platform signature and URL outputs, then uploaded with `gh release upload ... --clobber`. The Linux leg signs AppImage and .deb with `yarn tauri signer sign` using `TAURI_SIGNING_PRIVATE_KEY` (and password) from secrets.[40][5]
- Jan also pipelines delta-openssl/S3 staging for update payloads through `DELTA_AWS_*` secrets, and its ARM64 leg is treated as optional: if `windows-arm64` fails, `latest.json` is still published with a blank arm64 signature and a warning comment in the workflow.[5][7]

### AnythingLLM

The public Mintplex-Labs/anything-llm repo exposes no desktop-build workflow (its `.github/workflows` list has image-build, lint, test and QA workflows only); desktop installers appear on the GitHub releases but the CI that builds them is not visible in the public tree. Where those desktop builds run is NOT VERIFIED.[4]

### Open-webui

The main repo has `release.yml`/`release-pypi.yml` (PyPI publishing) and `docker.yaml`; no GitHub-release binary assembly (consistent with zero release assets).[41]

## 3. Update mechanisms in the wild

### Jan: Ed25519-signed static JSON manifest (the closest analog to Steward's design)

Jan publishes `latest.json` on each release. The actual file for 0.8.8 (fetched 2026-11-19) has this shape: `version`, `notes`, `pub_date` (RFC 3339), and a `platforms` map keyed `linux-x86_64`, `windows-x86_64`, `windows-aarch64`, `darwin-aarch64`, each with `signature` (base64) and `url` pointing at the release asset. The decoded base64 signature begins "trusted comment: signature from tauri secret key".[8]

This is the Tauri updater static-JSON format. Tauri's documentation states the updater "needs a signature to verify that the update is from a trusted source. This cannot be disabled," the public key is baked into `tauri.conf.json`, and the signature is a per-build Ed25519 signature over the artifact; the endpoint can be a dynamic server URL or "a static github json file", with `{{target}}` and `{{arch}}` variables when server-side. It also documents that losing `TAURI_SIGNING_PRIVATE_KEY` means you "will NOT be able to publish new updates to users that have the app already installed".[20]

### AnythingLLM: version.txt

AnythingLLM publishes a bare `version.txt` asset on each desktop release. How the desktop client consumes it (whether against the GitHub release or a Mintplex-hosted endpoint) is NOT VERIFIED from public sources; no desktop update code is visible in the public repo.[4]

### Ollama: signed check to a server endpoint plus platform-signature verification

Ollama's in-app updater is Go code in `app/updater/updater.go` (read 2026-11-19). It does NOT use a downloadable signed manifest. Instead:[36]

- Every hour the app calls `https://ollama.com/api/update?os=..&arch=..&version=..&ts=..` with a device nonce and signs the request with the device's keypair (`auth.Sign`); the server responds `204` when current or `{url, version}` otherwise.
- The download is staged by ETag, and before install it calls `VerifyDownload()`. On Windows (`updater_windows.go`) that verifies the installer's Authenticode signature via `crypto/x509` (`verifyWindowsInstallerSignature`); on macOS (`updater_darwin.go`) it verifies the bundle's code signature. So for Ollama the trust root is the platform code-signing signature of the fetched installer, not a signed manifest the app itself checks.[37][38]

### Package-manager driven updates (not self-update)

- Ollama macOS: a Homebrew cask `ollama-app` exists with `auto_updates true`, a pinned SHA-256 of `Ollama-darwin.zip`, `depends_on macos: :sonoma`, and both an app artifact and the `ollama` binary. Homebrew manages updates for those users instead of the in-app updater, and this split is an observed source of bugs (Section 6).[15]
- Ollama Windows: it maintains a per-version manifest set in `microsoft/winget-pkgs` under `manifests/o/Ollama/Ollama` (hundreds of version folders including 0.40.16), so `winget` is a supported channel.[16][29]
- Jan: present in both winget-pkgs (`manifests/j/Jan/Jan`) and Homebrew (`Casks/j/jan.rb`, with arm/intel/Linux SHA-256s including `x86_64_linux`), so Jan ships side-by-side channels: GitHub-releases self-update (Tauri) plus winget and brew for users who prefer a package manager.[30][43]
- AnythingLLM: a Homebrew cask exists (`Casks/a/anythingllm.rb` confirmed to exist, 2026-11-19).[42]

Bottom line for update strategy: the industry-standard pattern for "app checks its own updates" is an Ed25519-signed JSON manifest (Tauri style, exactly what Jan publishes and what Tauri requires), published as a release asset to the same GitHub release where the binaries live, with platform code-signing as an additional layer; the Ollama pattern (signed request to a proprietary endpoint, verify by platform signature) is the alternative used by a product that hosts its own server.[8][20][37]

## 4. What a public repo needs on day one for credibility and safety

### License

- Ollama is MIT (`license.spdx_id: MIT` via the GitHub API, 2026-11-19). AnythingLLM is MIT (same API check). Both repos carry a LICENSE file explaining the terms in addition to the SPDX field.[1][4]
- Jan and open-webui both return `NOASSERTION` for the license field on the GitHub API even though they are publicly distributed open-source products; Jan's actual LICENSE file is a customized text. Lesson: the GitHub license field being clean is not the norm, but "clean SPDX + standard MIT/Apache" is the low-friction, low-risk path Steward can hit with zero lawyers (matching its own MIT claim).[1][3][41]

### SECURITY.md and a private reporting path

- GitHub supports a `SECURITY.md` security policy per repo, and documents that private vulnerability reporting is a separate feature you must explicitly enable on the repo; the policy is displayed above the form when reporters use it.[34][13]
- AnythingLLM's SECURITY.md (read 2026-11-19) is a strong real example: all reports must go through GitHub Security Advisories (GHSA), the team states it ignores other platforms, it accepts PRs for low-severity obvious-fix issues, provides a contact email for triage questions, and it explicitly enumerates invalid report classes with a warning that repeated low-effort submissions get the reporter blocked. This is the modern, defensive SECURITY.md style.[9]
- Ollama's SECURITY.md is terse: do not open a public issue, report via GitHub advisories, include description/reproduction/impact, and allow time before disclosure.[39]
- Both also route through GitHub's private vulnerability reporting, which on public repos lets anyone file a private draft advisory that the maintainer can fix and publish as a GHSA with the reporter credited.[13]

### CONTRIBUTING and issue templates

- Every product examined ships a `.github/ISSUE_TEMPLATE/` directory with typed templates plus a `config.yml` chooser: Ollama has `10_bug_report.yml`, `20_feature_request.md`, `30_model_request.md`; Jan has bug/feature/epic/goal templates; AnythingLLM has bug, feature, documentation, and integration-request forms; open-webui has bug (yaml form) and feature-request templates. GitHub documents the template mechanics (YAML issue forms, `.md` templates, chooser config) so this is all standard plumbing.[1][3][4]
- AnythingLLM's CONTRIBUTING.md (read 2026-11-19) is a real-world example of a firm contribution policy: PRs without a linked issue are not merged (translations excepted), new features require a maintainer-approved issue first, some issues are labeled `core-team-only` and PRs against them are closed unread, and security issues are explicitly excluded from public issues.[10]
- Ollama also ships CONTRIBUTING.md, AGENTS.md and SECURITY.md at repo root, and the release workflow generates release notes from commits (`--generate-notes`), which is the cheap default for keeping release notes credible.[2][39]

### DCO vs CLA

- The Developer Certificate of Origin is a per-commit certification (`Signed-off-by`), introduced by the Linux Foundation in 2004, published at developercertificate.org.[23][24]
- Node.js runs a DCO model and embeds the full DCO text directly in its CONTRIBUTING.md, including the exact (a)/(b)/(c) certification clauses; contributors sign off commits rather than signing a contributor agreement.[22]
- The public discussion (opensource.com) frames the trade: DCOs are a low-barrier per-commit sign-off; CLAs are a heavier legal instrument. Kubernetes is widely documented as using a DCO model. For a solo/partner-run project with MIT code, the DCO is the standard low-friction choice and can be enforced mechanically by checking for `Signed-off-by` on PRs.[24][23][22]
- Closely related: GitHub's commit-signature verification documentation notes that a signature carries a timestamp record, so previously verified commits keep their verified status even if a signing key is later revoked or rotated. Practical implication for Steward: tag and release signing identities should be treated as long-lived records, and the DCO is enforced at the commit/PR level, not by any key record.[28]

### Keeping signing keys and proprietary bits out of the public tree

Primary evidence from workflows and docs, not folklore:

1. Keys live in GitHub encrypted secrets, never in the repo. Ollama's release workflow reads `APPLE_*`, `MACOS_SIGNING_KEY*`, `GOOGLE_SIGNING_CREDENTIALS`, `OLLAMA_CERT`, `KEY_CONTAINER` etc. from the `release` environment's secrets; Jan reads `CODE_SIGN_P12_BASE64`, `NOTARY_*`, `AZURE_*`, `TAURI_SIGNING_PRIVATE_KEY*` the same way. A base64 `.p12` is still a secret, stored in the Actions secret store, decoded only inside the runner.[2][6][7]
2. GitHub Environments gate the release pipeline: Ollama puts `environment: release` on every build job, which lets the repo require approvals or restrict which branches/tags can consume those secrets. This is the concrete mechanism for "only the release pipeline can sign."[2]
3. Keys that must be rotated are conveniently revocable if stored remotely: both Ollama (Windows, via Azure Key Vault KMS CNG) and Jan (Windows, via Azure sign.ps1) sign using keys held in Azure, so the private key never lands on the runner and can be revoked centrally without touching a compromised box.[2][7]
4. Sensitive local files stay ignored: Jan's `.gitignore` ignores `.env` and `.env.*`, the standard place app secrets and signing-password env files would go.[44]
5. GitHub's own remediation guidance for leaked secrets is explicit and currently the canonical procedure: treat a leaked secret as immediately compromised, revoke (not just delete) it with the provider, rotate, then consider history rewriting; secret scanning is free on public repos and GitHub auto-revokes leaked PATs in public repos; push protection blocks secrets from being committed.[21]
6. Microsoft's Windows code-signing guidance contains a direct warning relevant to agent-assisted development: do not let an AI agent create, export, or commit release certificates or signing credentials; keep them in a secrets manager or the build system's secure storage.[18]

## 5. Distribution channels: what is actually required

### winget (Microsoft's winget-pkgs)

Official procedure documented by Microsoft (learn.microsoft.com "Submit your manifest to the repository", last updated 2026-03-24; plus the actual Ollama submission as an observed example):[11]

- Manifests live at `manifests/<letter>/<publisher>/<application>/<version>/` in the `microsoft/winget-pkgs` repo (e.g. `manifests/o/Ollama/Ollama/0.40.16/`), submitted by forking with a blob:none/no-checkout clone and a sparse checkout, one version per PR, one PR per version.
- The modern manifest is a set of YAML files: a version manifest, an installer manifest, and one or more locale manifests. Ollama's 0.40.16 set is `Ollama.Ollama.installer.yaml`, `Ollama.Ollama.locale.en-US.yaml`, `Ollama.Ollama.locale.zh-CN.yaml`, `Ollama.Ollama.yaml`, and the version manifest declares `ManifestVersion: 1.28.0` and `PackageVersion: 0.40.16`.[29][16]
- On PR, automated validation runs: schema checks, installer scans by several antivirus engines, install/uninstall tests for admin and non-admin, and URL sanity. PRs carry status labels (`Azure-Pipeline-Passed`, `Needs-Author-Feedback` with a 10-day auto-close, `Validation-Completed`, `Blocking-Issue`, `Binary-Validation-Error`). A manual moderator review follows; Microsoft says it may refuse any submission.[11]
- Policy requirements that matter for an installer: silent/non-interactive install support, the installer must come directly from the publisher's site, install and uninstall must work for normal users, and the binary must pass the antivirus scans. A `Binary-Validation-Error` (PUA detection) is a hard rejection that forces a code change; false positives are escalated to the AV vendor first.[11]
- The winget catalog is a separate artifact from the GitHub repo; merging into winget-pkgs is what makes `winget install` discover it. Submission is a fork-and-PR loop, not an API.

### Homebrew cask / tap

Official docs (docs.brew.sh "Adding Software to Homebrew", retrieved 2026-11-19):[12]

- A formula is for software Homebrew builds from source; a cask is for binary-only / native desktop applications, which is the relevant type for Steward. Casks may target macOS, Linux, or both, but only the platform's supported artifact types.[12]
- Process: check acceptance policies (`Acceptable-Casks`, `Package Acceptance Policy`), search existing closed PRs, fork `homebrew/homebrew-cask`, create the cask file with a verified immutable release URL and SHA-256 (or `sha256` arm/intel blocks) per the Cask Cookbook, test locally with `brew install --cask`, `brew audit`/`brew style`, run `brew lgtm --online` from the checkout, then open a PR from a branch with the template filled in.[12]
- Observed examples that made it through: `ollama-app.rb` (pins `Ollama-darwin.zip` SHA-256, declares `auto_updates true` and `depends_on macos: :sonoma`), `jan.rb` (ARM/Intel/`x86_64_linux` SHA-256s), and `anythingllm.rb`.[15][30][42]
- Homebrew casks conventionally point at GitHub release URLs with `version` interpolation (`url "https://github.com/ollama/ollama/releases/download/v#{version}/Ollama-darwin.zip"`), and `livecheck` uses `strategy :github_latest` so the cask is auto-updated from GitHub release tags. Publishing to the default cask tap is a PR; a self-hosted tap (`brew tap user/tap`) is the alternative that needs no approval.[15]
- Note: cask `auto_updates true` for Ollama coexists with a separate in-app updater, and that coexistence is exactly what produced a documented bug (Section 6), so it is worth choosing one owner for updates per installation method.

## 6. Failure modes: documented cases and mitigations

### Compromised build tooling exfiltrating CI secrets (Codecov, 2021)

The Codecov Bash Uploader compromise is the canonical documented case of a release/supply-chain pipeline leak. From Codecov's own April 2021 post-mortem: an attacker obtained a GCS key from a Docker image layer, then maliciously altered the bash uploader so that every customer who ran it (bash uploader, GitHub Action, CircleCI orb, Bitrise step) had git remote origin URLs and environment variables exported to the attacker's server, for about three months before detection. The incident was first detected on April 1, 2021 by a customer who SHA256-checked the uploader and found the checksum did not match GitHub's. Mitigations Codecov took: revoked the stolen key and rotated all production keys, squashed/multistage Docker builds, shipped a new signed and checksum-verifiable uploader binary, added change monitoring, and built a key-generation/rotation/audit tracking tool.[25]

Relevance to Steward: a CI step that pipes arbitrary code (`curl | bash` style) is the supply-chain top risk for release pipelines; the mitigation pattern is pinned checksums, signed release tooling, least-privilege secrets, and audit/rotation tooling exactly as Codecov adopted.

### Unsigned Windows installer hit by SmartScreen (open-webui, and Microsoft's own terms)

open-webui/desktop issue #117 documents a product in Steward's exact position: the `open-webui-setup.exe` installer is not Authenticode-signed, so a standard Windows 11 machine shows "Windows protected your PC ... Publisher: Unknown publisher", which is a blocker in enterprise/managed environments and a trust problem for consumers who must click "Run anyway". Opened against the latest release; open as of this study.[17]

Microsoft's own current documentation quantifies the consequences (retrieved 2026-11-19; smart-screen-reputation page last updated 2026-05-06): an unsigned file always shows the "Windows protected your PC" warning and users must choose "Run anyway"; enterprise policy can prevent continuation entirely; unsigned files build reputation anew from zero with every version because reputation cannot transfer across unsigned versions. EV certificates no longer bypass SmartScreen (behavior removed in 2024), so the old "buy an EV cert" shortcut is gone; OV certificates and Azure Trusted Signing (~USD 9.99/month) both show warnings until reputation accumulates over "several weeks and hundreds of clean installs". The documented mitigations are: sign every release with a consistent publisher identity so certificate reputation carries across versions, publish to the Microsoft Store to be re-signed by Microsoft and skip warnings entirely, and communicate the expected first-run warning to early adopters. Microsoft's code-signing options page adds that Artifact Signing (formerly Trusted Signing) is Microsoft's recommended non-Store path and integrates with GitHub Actions.[19][18][33]

### macOS Gatekeeper blocks unsigned / un-notarized apps

Apple's own support page (published 2026-05-27) states that on macOS Catalina and later, software must be signed and notarized by default; running software that has not been signed and notarized can expose the machine, and an unsigned app requires the user to override security settings ("Open Anyway") in System Settings. Apple's Developer ID page frames it as: Gatekeeper checks for a Developer ID certificate for apps distributed outside the Mac App Store, and notarization additionally tells Gatekeeper the app was scanned by Apple.[31][32]

A concrete GitHub-released example: the local-dictate project's v0.1.2 release notes state plainly "These builds are not notarized" and tell users to clear the Gatekeeper quarantine flag (xattr) after install. This is the standard, explicit friction a notarization-less project ships to its users today, versus a notarized release which opens cleanly.[27]

Mitigation path (as implemented by Ollama and Jan, Section 2): macOS builds codesign with a Developer ID and notarize via `xcrun notarytool`/Tauri using secrets, then verify the stapled ticket in CI (Jan even added an explicit post-build `codesign --verify --deep` gate for nested binaries). That is the actual mitigation, and it is observable in their workflow files.[6][2]

### Broken auto-update: in-app updater fights the package manager (Ollama issue #11336)

Ollama issue #11336 (opened 2026-07-09) documents a failure mode directly relevant to Steward's update design: with Ollama installed via Homebrew, the in-app "Restart to update" flow stopped working (clicking restart re-opened settings instead of restarting), the app restarted at the old version, and users had to fall back to `brew` remedies; the maintainers labeled it `install`/`app`/`macos` and later scoped the title to "when installed via brew". The coexistence of an in-app self-updater and a package manager (Homebrew cask `ollama-app` with `auto_updates true`) is the root friction, and the issue stayed open.[26][15]

Mitigation guidance that follows directly from this and from the artifacts: pick one update owner per installation method. If Steward ships a brew cask / winget manifest, package-manager users should update via the manager, and the signed-manifest self-update path should be reserved for direct-download installs (or the app should detect the package-manager install and defer), so two updaters never race to write the same app bundle.

### Truncated or corrupted update being applied (oligolia issue #48)

A small-project issue (moonsoup/oligolia #48) documents an auto-updater that downloaded a truncated/partial patch and applied it over the live `.app` bundle, bricking the installed app; the root cause was in the updater's own download/apply logic. I verified only the issue title and summary text via search, not the full thread, so the detail here is limited to what the issue summary states (see NOT VERIFIED). It is a representative caution for the class of bug that a signed-manifest updater plus a verify-before-install stage (as Ollama's `VerifyDownload()` does, Section 3) exists to prevent.[36][37][38]

### Leaked secrets and the correct response

For the "what to do if a signing key leaks" problem, the authoritative current procedure is GitHub's own remediating-a-leaked-secret tutorial: consider the secret immediately compromised, revoke it with the provider first (deleting the commit is not enough), rotate, then optionally rewrite history; and there is no scenario where merely unpublishing the file is a fix. It also states GitHub automatically revokes leaked PATs in public repos, and that secret scanning is free on public repositories, with push protection able to block secrets at commit time.[21]

## 7. Findings that most directly change what Steward should do

Each finding is stated with its evidence in the sections above.

1. Publish the update manifest as a release asset next to the binaries, exactly as Jan does. Steward's stated design (Ed25519-signed JSON manifest checked by the app) is the de facto industry standard in this exact product niche: it is literally what Jan publishes on every release and what Tauri requires, and the rich validation logic (version, pub_date, per-platform signature + URL) is already documented and battle-tested.[8][20]
2. One GitHub release per version, multi-asset, with a generated checksum file covering every payload. Ollama's final job verifies a required-artifact list, generates `sha256sum.txt` at the end, uploads it last with `--clobber`, and creates releases as drafts first. Steward can lift this pattern wholesale: tag `v*`, assemble per-platform bundles, checksum, publish once, checksum last.[2][1]
3. Build natively per OS on GitHub-hosted runners (no cross-compile for app bundles): Ollama uses `macos-26-xlarge`, `windows`, `linux`, `linux-arm64`; Jan defaults to `windows-2025`, `macos-latest`, `ubuntu-22.04` via reusable workflow templates. Reusing template workflows like Jan's keeps one build definition per platform without copy-paste drift.[6][7][40]
4. Put every signing secret behind a GitHub Environment (`environment: release`) and never in the tree; store Apple certs as base64 secrets and Windows keys in Azure Key Vault so a compromised runner cannot exfiltrate the private key material. Both reference projects do this, and Microsoft's own docs add the agent-specific warning against committing signing credentials.[2][7][18]
5. Without a Windows code-signing cert, Steward's Windows installer will hit SmartScreen "Unknown publisher" on every first run for every version, and enterprise policy can block it entirely. Signing changes the wording but not the early warning: reputation builds over weeks/hundreds of installs, and EV certs no longer skip it (2024). If Steward signs, it must keep one consistent publisher identity across all releases or reputation never accumulates. Azure Trusted Signing at ~USD 9.99/month is the current realistic non-Store option, and publishing to the Microsoft Store removes warnings by re-signing with Microsoft's cert.[19][18][17]
6. macOS distribution effectively requires Developer ID signing plus notarization since Catalina; an un-notarized release ships with an "Open Anyway"/quarantine-clearing instruction (observed in a real release today), which is a credibility tax Steward would pay until it has an Apple cert. Notarization is automatable in CI with App Store Connect API secrets, exactly as Ollama and Jan do.[31][32][27]
7. Only rely on one update mechanism per install channel. The Ollama/Homebrew clash (in-app updater against a `auto_updates` cask) is a documented open bug; Steward should detect package-manager installs and let the manager update, or not claim `auto_updates` in the cask it publishes.[26][15]
8. Do not publish to winget/Homebrew until the artifacts are ready to pass their validation bars: winget scans installers with multiple antivirus engines, requires silent install/uninstall for normal users, and one-version-per-PR through a manually moderated review; Homebrew casks require immutable release URLs with pinned SHA-256s and pass `brew audit`. Both are fork-and-PR processes, not APIs, and both (Ollama, Jan) already hold manifests Steward can copy as templates.[11][12][29]
9. Day one for the public repo is cheap and fully standardized: MIT LICENSE, a SECURITY.md routing reports to GitHub Security Advisories with the private-vulnerability-reporting feature enabled, a CONTRIBUTING.md with a DCO (Node.js and anything-llm are concrete templates), and a typed `.github/ISSUE_TEMPLATE/` set. Every product studied has all of these; nothing here requires legal counsel beyond the SPDX license field.[13][34]
The DCO example is established practice, and the contribution policies above carry their own citations.[22][9][10] (See also the template docs.)[35]
10. Defense against the classic failure: verify release inputs with pinned checksums and do not let release CI run unpinned third-party scripts; the Codecov case shows a tool that read CI environment variables exfiltrated months of secrets and was only caught by a customer's checksum check. Secret scanning (free on public repos) plus push protection should be enabled before the repo goes public, and every signing key should be registered for rotation/audit with a documented owner.[25][21]
11. Anything Steward can publish about "how the app verifies updates" is a selling point and a review target: Tauri documents that the signature requirement "cannot be disabled," and Ollama's updater refuses to install until the fetched installer's platform signature verifies. Steward's Ed25519 manifesto should be presented the same way and documented in SECURITY.md so reviewers can audit it.[20][36][37]
